# Инструкция для агента: один `slide.md` на проект

Документ для **агента из другого репозитория**. Его задача — по вашему коду/README написать **один файл** `slide.md`: описание **одного проекта** для вставки в HTML-презентацию [show](https://github.com/timptr42/show).

---

## Для кого текст (главное про стиль)

**Аудитория:** сотрудники **смежных подразделений**, которые **не погружены** в ваш проект (менеджмент, соседние команды, поддержка, аналитика — не только разработчики).

**Как писать:**

1. **Сначала** — общая идея **простым языком**: что болит, что сделали, зачем это команде.
2. **Потом** — технические детали **кратко**, без углубления (стек, названия сервисов — по делу, 2–4 пункта).

| Плохо | Хорошо |
|--------|--------|
| «Дедупликация по fingerprint в Alertmanager» | «Одинаковые алерты больше не сыпятся пачкой — система склеивает их в одно сообщение» |
| «Раннер на Playwright + Allure» | «Автопроверка интерфейса в браузере; в конце — понятный отчёт, что сломалось» |
| Длинная таблица из 8 технологий | 2–3 инструмента и одна фраза, зачем каждый |

**Избегать:** внутренний жаргон без пояснения, аббревиатуры без расшифровки, длинные листинги кода, предположение что все знают ваш репозиторий.

**Объём:** короткие фразы, 2–4 буллета на слайд; на весь блок — примерно **2–3 минуты** устного рассказа.

---

## Главное (частая ошибка)

| Нужно | Не нужно |
|--------|----------|
| **Один** файл `slide.md` | Каталог `in/` целиком |
| **Один** проект / одна история | Несколько папок `01-…`, `02-…`, `03-…` |
| `type: talk` | `00-welcome`, `99-questions`, `type: welcome` |
| Текст в Markdown | Сборка `build.py`, HTML, структура выступления |

Заглушка, финальные вопросы и остальные блоки презентации **уже есть в show**. Их **не создаёт** агент из чужого репозитория.

**Неверно** (так делать не надо):

```
in/
  00-welcome/slide.md
  01-owui-web-tester/slide.md
  02-provider-diagnostics/slide.md
  03-runner-reporting/slide.md
  99-questions/slide.md
```

**Верно** — агент отдаёт **только это** (содержимое одного файла):

```
slide.md   ← один файл, один проект
```

Организатор выступления сам положит его, например, в `in/11-owui-web-tester/slide.md` и добавит картинки/видео рядом.

---

## Что сдать

### Обязательно

1. **Один** `slide.md` с `type: talk`.
2. Внутри — **ровно 5 секций** с заголовками `##` (см. ниже).
3. Язык: **русский**, простой, для «чужого» подразделения; устный доклад, без перегруза.

### Опционально (отдельным списком в конце ответа)

Список медиа, которые нужно положить **в ту же папку**, что и `slide.md` (их может добавить человек, не агент):

- `scheme.svg` — если в «Решение» есть `![](scheme.svg)`
- `demo-01.mp4`, `demo-02.svg`, … — 1–3 файла, по одному на демо-слайд

Агент **может** сгенерировать SVG-схему, если умеет, но **не обязан** создавать дерево папок.

---

## Если в репозитории несколько подсистем

Выберите **одну линию для одного выступления** (один `slide.md`):

- либо весь репозиторий как **одна история** (общая проблема → общее решение),
- либо **одна** ключевая фича (например, только «web tester», без отдельных блоков на diagnostics и reporting).

**Не разбивайте** один репозиторий на несколько `slide.md` и папок `01-`, `02-`, `03-` — для этого вызова нужен **один** блок.

---

## Frontmatter (в начале файла)

```yaml
---
title: "Короткое название проекта"
author: "Имя · команда или роль"
type: talk
---
```

- `type` — **всегда** `talk`.
- Не используйте `welcome` и `questions`.

---

## Пять обязательных секций

Заголовки **точно** так (сборщик ищет их по тексту):

```markdown
## Проблема
## Инструменты
## Решение
## Демо
## Вопросы?
```

В **каждой** секции соблюдайте порядок: **сначала смысл простыми словами → потом кратко техника**.

| Секция | Сначала (простым языком) | Потом (кратко, техника) |
|--------|---------------------------|-------------------------|
| **Проблема** | Что мешало работе / людям / заказчикам; без названий классов и модулей | При желании — 1 цифра или 1 короткий факт («раньше — N часов в неделю») |
| **Инструменты** | Не обязательна отдельная «простая» часть — перечислите **2–4** средства **с пояснением роли** («X — чтобы …») | Без глубокой архитектуры; таблица только если ≤4 строк |
| **Решение** | **Одно-два предложения:** что теперь есть и какую пользу даёт | 2–3 буллета «как устроено»; схема `![](scheme.svg)` — простая, без мелких подписей |
| **Демо** | Что увидит зал своими глазами («покажем, как …») | Не нужны имена файлов и фреймворков |
| **Вопросы?** | Вопросы, которые мог задать **неспециалист** («а если отключится …?») | Не вопросы только для maintainer’ов |

Заголовки секций в MD **не менять** — меняется только стиль текста внутри.

В готовой презентации порядок слайдов: Проблема → Инструменты → Решение → Демо (медиа) → Вопросы?

Порядок секций **внутри файла** может быть любым.

### Markdown внутри секций

- Абзацы, **жирный**, списки `-` (короткие пункты, одна мысль — одна строка)
- Таблица — только если без неё хуже; не больше **4 строк**
- Код и CLI — **не использовать**, максимум одна строка `текст → текст` схемой слов
- Картинки: `![](имя-файла.svg)` — схема «для людей», не для разработчиков

---

## Медиа (справка, не путать с заданием агента)

| Назначение | Файлы | Кто обычно добавляет |
|------------|--------|----------------------|
| Схема в «Решение» | `scheme.svg` и т.п., ссылка `![](scheme.svg)` в MD | человек или дизайнер |
| Демо-слайды | `demo-01.*`, `demo-02.*` — кладутся в папку блока; показ после `## Демо` | человек (скрин/видео) |
| Фон welcome/Q&A | видео в `00-welcome` / `99-questions` | **не** этот агент |

Полные правила: [IN_FORMAT.md](IN_FORMAT.md). Демо-видео в презентации **не автозапускаются** — только Play в плеере.

## Полный пример ответа агента

Ниже — **весь** ожидаемый результат (один MD-файл + короткий список медиа).

### Файл `slide.md`

```markdown
---
title: "OWUI Web Tester"
author: "Команда платформы"
type: talk
---

## Проблема

После каждого обновления чата приходилось **вручную** проверять одни и те же сценарии — это отнимало время и ошибки находили поздно.

- Не было единого чек-листа «что обязательно проверить»
- Результаты проверки каждый раз описывались по-разному

## Инструменты

- **Автотесты в браузере** — имитируют действия пользователя в интерфейсе
- **Скрипт запуска** — один раз нажали — получили отчёт
- **Отчёт в одном формате** — сразу видно, что упало

## Решение

Сделали **автоматическую проверку** интерфейса: один запуск → один понятный отчёт для команды.

- Сценарии хранятся в репозитории, их не нужно искать в чатах
- После прогона видно список успешных и упавших проверок

![Как это работает](scheme.svg)

## Демо

Покажем: нажимаем «запуск» — через минуту открываем отчёт с зелёными и красными пунктами.

## Вопросы?

- Нужно ли гонять проверки каждую ночь без участия человека?
- Кто будет обновлять сценарии, когда поменяется интерфейс?
```

### Список медиа (текстом, не как дерево `in/`)

- `scheme.svg` — блок-схема: сценарии → runner → отчёт  
- `demo-01.mp4` — запись прогона (опционально)  
- `demo-02.svg` — скрин отчёта (опционально)

---

## Чеклист перед ответом

- [ ] Отдан **один** `slide.md`, не каталог `in/`
- [ ] Нет `00-welcome`, `99-questions`, нет второго/третьего talk-блока
- [ ] `type: talk`
- [ ] Есть все 5 заголовков `## Проблема` … `## Вопросы?`
- [ ] В «Демо» — текст, что показать, а не три отдельных «проекта»
- [ ] Текст понятен **без знания** репозитория; сначала идея, потом техника
- [ ] Нет перегруза терминами; ~2–3 минуты рассказа на блок

---

## Чего не делать

- Не создавать `in/00-welcome`, `in/99-questions`, несколько `in/01-*`
- Не предлагать «сократить до 2 блоков» или «расширить до 5» — нужен **один** блок на этот репозиторий
- Не менять названия секций (`## Проблема` и т.д.)
- Не писать HTML
- Не запускать `build.py` (это делает владелец show)
- Не писать «для разработчиков» — без расшифровки жаргона и длинного стека

---

## Контекст show (для понимания, не для генерации)

Репозиторий show уже содержит каркас презентации (`00-welcome`, блоки `01-`…`10-`, `99-questions`). Сборка: `python build.py` → `out/index.html`. Формат файлов: [IN_FORMAT.md](IN_FORMAT.md).

Ваш `slide.md` — **один новый или заменённый блок** в этой цепочке.
